# Data and Model Poisoning

## Overview

Machine learning systems, particularly large language models (LLMs), rely heavily on the quality of the data used during training. These models are trained on vast collections of text gathered from multiple domains, languages, and writing styles. While this diversity improves model capability, it also creates opportunities for attackers to tamper with the data.

**Training data poisoning** occurs when malicious or misleading information is intentionally inserted into the datasets used to train or refine a model. If such manipulated data is introduced during any stage of model development—pre-training, fine-tuning, or embedding generation—it can cause the model to learn incorrect patterns, hidden triggers, or biased behaviors.

As a result, the model may generate misleading answers, expose system weaknesses, or produce outputs that damage an organization’s reputation.

---

## Points in the Training Pipeline Where Poisoning Can Occur

Poisoning attacks can target multiple stages of the model lifecycle.

### 1. Pre-Training Phase

During pre-training, a model learns general language patterns from very large datasets. These datasets often come from multiple external sources.

If malicious data is injected at this stage, it can subtly influence the model’s foundational knowledge. Techniques such as **Split-View poisoning** or **Frontrunning poisoning** can manipulate how the model interprets information, embedding harmful behaviors deep into the model.

Because pre-training datasets are extremely large, detecting small amounts of malicious content can be difficult.

---

### 2. Fine-Tuning Phase

Fine-tuning is performed after pre-training to adapt the model for a specific task. This process uses a smaller, carefully structured dataset consisting of example inputs and expected outputs.

If the fine-tuning dataset contains incorrect, biased, or manipulated entries, the model may learn undesirable behavior. For example:

- Producing unsafe or biased responses  
- Giving incorrect domain-specific advice  
- Responding incorrectly to specific trigger inputs

Since fine-tuning datasets are typically curated manually or sourced from external providers, poor validation practices increase the risk of poisoning.

---

### 3. Embedding Generation

Language models convert text into numerical representations called **embeddings**. These vectors capture semantic relationships between words or concepts and are often used in search, retrieval systems, and recommendation engines.

If harmful or misleading data is introduced during this stage, it can distort the vector space. This may lead to:

- Incorrect similarity relationships
- Retrieval of malicious or irrelevant content
- Reduced model accuracy

Because embeddings are used in downstream tasks, compromised vectors can propagate errors across multiple systems.

---

## Impact of Data Poisoning

Data poisoning is primarily an **integrity attack**, meaning it affects the reliability of model outputs.

Potential consequences include:

- Incorrect or misleading responses generated by the model
- Hidden backdoors triggered by specific inputs
- Amplification of bias or unsafe behavior
- Exposure of sensitive information
- Damage to organizational credibility
- Regulatory or legal consequences in sensitive industries

Models trained with unverified or low-quality data may behave unpredictably, especially when the data originates from external sources that are not fully controlled by the organization.

Another risk arises when users unknowingly provide confidential information during interactions. If that information is incorporated into training data without proper filtering, the model might later reveal it in unrelated responses.

---

## Example Scenarios

### Financial Assistant Model

Consider a company building an LLM that acts as a financial advisory assistant.

The training dataset includes large volumes of third-party financial content gathered from external providers. If the integrity of these datasets is not verified, attackers could introduce misleading financial information or biased recommendations.

As a result, the model might provide incorrect financial guidance to users. In regulated industries such as finance, this could lead to regulatory penalties, financial losses, or reputational harm.

---

### Accidental Data Exposure

Another scenario occurs during normal user interaction.

A user may unintentionally include sensitive corporate information in a prompt while interacting with the system. If that interaction is logged and later reused in training datasets without sanitization, the model could learn from it.

In future interactions, the model might reproduce that confidential information when responding to other users, violating privacy and confidentiality requirements.

---

## Prevention Strategies

Reducing the risk of data poisoning requires strict controls over the entire model development pipeline.

### Dataset Validation

All training datasets should undergo thorough validation before being used. This includes:

- Reviewing datasets for anomalies or unusual patterns
- Checking for hidden bias or malicious entries
- Verifying the authenticity of external data sources

Automated tools can assist in detecting suspicious patterns such as abnormal text distributions or repeated triggers.

---

### Secure Data Supply Chain

Organizations should maintain visibility into the origin and transformation of training datasets.

One recommended approach is maintaining a **Machine Learning Bill of Materials (ML-BOM)**. This document tracks:

- Data sources
- Dataset versions
- Data transformations
- Model dependencies

Frameworks such as **OWASP CycloneDX** can help create and manage these inventories.

---

### Controlled Model Environment

LLMs should operate in a controlled environment that restricts access to untrusted content sources.

For example:

- Prevent the model from scraping arbitrary internet content
- Isolate the model within a sandbox environment
- Apply strict access controls to training pipelines

This reduces the likelihood of malicious content entering the training process.

---

### Data Sanitization

Before training, datasets should pass through filtering and cleansing mechanisms such as:

- Anomaly detection
- Outlier analysis
- Sensitive data removal
- Content filtering

These techniques help identify and remove potentially harmful data points.

---

### Model Testing and Monitoring

Continuous monitoring is essential for detecting poisoning attempts.

Recommended practices include:

- Monitoring unusual response patterns
- Investigating spikes in incorrect or biased outputs
- Conducting periodic manual dataset reviews
- Performing red-team testing to simulate adversarial attacks
- Running automated LLM vulnerability scans

If abnormal behavior is detected, the associated training data should be re-examined.

---

### Secure Model Updates

When updating models:

- Fine-tune using carefully curated datasets
- Track dataset changes using version control
- Maintain audit logs for training data modifications

This ensures that any introduced changes can be traced and verified.

---

### Safe Inference Techniques

Techniques used during inference can further reduce risks:

- **Retrieval-Augmented Generation (RAG)** to fetch verified information from trusted sources
- **Grounding mechanisms** that anchor responses to validated data
- Output validation to detect hallucinations or unsafe responses

These approaches help maintain reliable model outputs even if parts of the training data contain inaccuracies.
